# Customer portal

Apply migrations 017 and 018 with `npm run db:migrate` before releasing this version. Migration 017 commits the enum addition separately so PostgreSQL can use it safely in subsequent transactions. Migration 018 links customer accounts to clients with a required, restrictive foreign key. Back up the database before deployment.

Super Users manage customer logins in Users → Customer logins. Choose a client and create a password (12 characters minimum, 72 UTF-8 bytes maximum). Multiple customer contacts can share the same client. Customer accounts are managed separately from staff accounts; no report-column permissions or contract assignments are needed. Edit an account to change its client, disable access, reset its password or change print/export access. Every edit revokes existing sessions. Passwords must be delivered using a trusted channel; this change does not send invitations or implement first-login password changes.

The customer login URL is `/customer`; the existing root login also recognises customer accounts. Both use the same secure session and idle/absolute expiry rules. Customers see only their linked client's contracts and devices. Service history requires a finalized visit plus both engineer and customer signatures. History includes service status, fitted part identity/quantity and signatory names/times. Contract/device notes, audit history, raw report imports, stock, other clients and supporting attachments are deliberately excluded. Device-service comments, summaries/recommendations and signature images appear only in the signed service report download described below. No publication/backfill changes are made to existing visits.

Customers cannot call staff APIs, even if someone mistakenly adds a staff report/contract assignment to their account. Portal SQL derives client access from the authenticated account, never from caller-supplied client IDs. Responses use an explicit public-field allowlist and are not cached. One snapshot is used for each portal load. Current safety limits are 1,000 contracts, 10,000 contract devices and 10,000 device-service records per customer; oversized results return an error rather than silently truncating exports.

## Signed service reports

Customers whose login has print/export access see a **Signed report** button on each Service history row. It opens the same full service report staff print (device comments, parts fitted, summary, recommendations and both signature images) as a branded A4 print/PDF preview. The route `/api/customer-portal/service-visits/[id]` returns a visit only when it belongs to the account's own client, is finalized and has both the engineer and client signatures; otherwise it answers "not found". Logins without export access get a 403 and see no button. Each download is recorded in the activity log as an `exported` service-visit event. The service history list itself still excludes signatures, comments, summaries and recommendations.

## Callout requests

Every active customer login has a **Request a callout** tab. Customers choose a contract and device (optional), describe the problem, set Normal or Urgent, and can add a location and contact name/phone. The client is always taken from the signed-in account; a chosen contract and device must belong to that client and the device must currently be on the contract. A client can have at most 10 requests waiting for review. Customers see their requests' status: waiting for review, accepted (engineer assigned / on the way / completed, following the callout) or declined with the reason staff gave. They never see engineer names or internal callout details.

Super Users review requests under **Call-outs → Customer call-out requests**; new requests also count towards the Call-outs badge. **Accept and create call-out** creates a normal callout for the chosen engineer in the same transaction, with the customer's contact details and the request reference (`CR-…`) in its description. **Decline** requires a reason, which the customer sees. A request can only be decided once. Apply migration `020-callout-requests.sql` with `npm run db:migrate` before releasing.

## Filters, print and export

Contracts, devices and service history support filters, branded A4 print/PDF previews and formula-safe CSV previews. Print/export controls require the account's export setting; read access still inherently permits manual copying or browser printing. Printed history is a customer-facing summary with signatory names/times, not a replica of the internal signed service report. Existing portal data is a point-in-time view; refresh to see newly published visits. Revoked accounts/sessions are blocked on subsequent server requests; already viewed/downloaded data cannot be recalled.

Checks: `npm test`, `npm run check` and customer-portal browser smoke tests. Automated API tests simulate PostgreSQL; verify migrations and two distinct clients against staging PostgreSQL before releasing customer access. No production migration, customer creation or deployment is performed automatically.
